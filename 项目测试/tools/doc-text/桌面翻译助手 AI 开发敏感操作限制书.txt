# 桌面翻译助手 AI 开发敏感操作限制书
**文档编号**：SEC-CONSTRAINTS-001
**版本**：v1.0
**生效日期**：M1 启动前
**适用对象**：参与本项目开发的所有 AI 编码助手（含 DeepSeek Harness Agent、Copilot、Claude Code 等）
**约束范围**：开发、调试、测试全过程中 AI 对本地环境、代码生成、数据访问的操作
## 1. 总则
### 1.1 目的
本限制书旨在约束 AI 编码助手在本项目开发过程中可能触及的敏感操作，防止因 AI 自主行为导致：用户数据泄露、凭据外泄、系统环境破坏、供应链污染、以及最终产品引入超出需求范围的安全风险。
### 1.2 依据
本限制书依据以下来源制定：
- DeepSeek Harness 官方安全模型：权限预设、沙箱模式、审批策略构成分层防线，Agent 应运行在最小权限预设下。
- OWASP LLM Top 10 2026：敏感信息泄露（LLM02）、过度代理（LLM03）、供应链（LLM04）为本项目直接相关风险。
- 微软 AI 辅助开发安全指南：AI 生成的代码由开发者负责，凭据不得进入提示词，权限申请应最小化。
- 本项目需求书 v2：屏幕采集范围限定为框选区域，离线优先，联网 API 由用户自配。
### 1.3 责任归属
**AI 生成的每一行代码，在合并入主分支前均视为“待审代码”，其安全责任由项目负责人承担。**“这是 AI 写的”不构成任何安全问题的免责理由。
## 2. 文件系统访问限制
| 编号 | 限制项 | 具体要求 | 违规处理 |
|------|--------|----------|----------|
| FS-01 | 允许访问范围 | AI 仅可读写项目工作目录（`$PROJECT_ROOT`）及其子目录 | 拒绝执行，记录审计日志 |
| FS-02 | 禁止访问路径 | 禁止读取、写入、列目录：用户主目录（`~`/`C:\Users\*`）、系统目录（`/etc`、`C:\Windows`）、其他应用数据目录（`AppData`、`Library`）、`.ssh`、`.aws`、`.env` 文件 | 拒绝执行 |
| FS-03 | 截图文件落盘 | 调试截图功能时，截图文件仅可存放于 `$PROJECT_ROOT/tmp/`，且每次调试结束后由 AI 主动删除 | 若检测到截图文件出现在其他路径，M1 验收不通过 |
| FS-04 | 删除操作 | 禁止执行 `rm -rf`、`del /s /q`、格式化、清空目录等破坏性文件操作。删除单个文件需显式声明路径并经人工确认 | 拒绝执行 |
**依据**：DSH 安全指南建议默认仅允许当前仓库，敏感目录应 deny；微软指南要求文件路径使用允许列表方法。
## 3. 命令执行限制
| 编号 | 限制项 | 具体要求 |
|------|--------|----------|
| CMD-01 | 禁止执行命令 | `rm -rf`、`format`、`reg delete`、`schtasks /delete`、`net user`、`shutdown`、任何修改注册表或系统服务的命令 |
| CMD-02 | 需人工确认的命令 | `npm install` / `cargo add` / `pip install` 引入新依赖前，须列出包名、版本、用途，经项目负责人确认后方可执行 |
| CMD-03 | 允许自动执行的命令 | `git status`、`git diff`、`ls`/`dir`、项目内构建命令（`cargo build`、`npm run dev`）、测试命令 |
| CMD-04 | 网络命令 | 禁止执行 `curl`/`wget`/`Invoke-WebRequest` 向项目指定的端点之外发送任何数据；调试翻译功能时仅可请求 `http://127.0.0.1:8081`（本地 llama.cpp）或 mock 服务 |
**依据**：Harness 安全设计将命令分为低/中/高风险三级，高风险禁止或走审批；DSH 权限预设中的 `workspace-write + ask` 模式可作为工具层兜底。
## 4. 凭据与密钥处理限制
| 编号 | 限制项 | 具体要求 |
|------|--------|----------|
| KEY-01 | 禁止读取真实凭据 | AI 不得读取、打印、记录任何真实 API Key、加密密钥、密码、Token。开发调试使用占位符（如 `sk-test-placeholder`） |
| KEY-02 | 禁止写入代码 | AI 生成的代码中不得包含硬编码的凭据，包括占位符形式的硬编码。凭据必须从配置存储或环境变量读取 |
| KEY-03 | 禁止写入日志 | 代码中不得包含将 API Key 写入日志、错误消息、遥测的逻辑。调试输出中如涉及 Key，必须掩码为 `sk-****` |
| KEY-04 | 用户 API Key 的处理 | M4 配置面板中，用户填入的 Key 在宿主壳内存中解密后传递至翻译插件，AI 不得在代码中添加任何将 Key 写入磁盘明文、发送至非用户配置端点、或记录到日志的逻辑 |
**依据**：OWASP LLM02（敏感信息泄露）要求凭据不进入模型上下文；微软指南明确“从不将 API 密钥粘贴到提示中”，AI 常生成 `your-api-key-here` 占位符，应视为缺陷。
## 5. 屏幕采集与 OCR 限制
| 编号 | 限制项 | 具体要求 |
|------|--------|----------|
| SCR-01 | 采集范围 | 调试截图功能时，仅可采集需求书 F-09 定义的框选区域（矩形坐标由测试用例指定），禁止全屏采集、后台持续截屏、定时截屏（除非测试用例明确要求且单次运行不超过 30 秒） |
| SCR-02 | 截图内容 | 测试用截图不得包含真实用户桌面内容（邮件、聊天记录、文档）。使用合成图像（如纯色背景 + 渲染文本）或公开测试图 |
| SCR-03 | OCR 输出处理 | OCR 识别出的文本在调试中仅可输出到终端或项目内日志文件，不得发送至任何外部服务（本地 llama.cpp 除外） |
| SCR-04 | 权限申请 | 宿主壳代码中申请的系统权限（屏幕录制、辅助功能）必须与需求书 F-09/F-10 范围一致。AI 不得在代码中添加超出“框选区域截图”所需权限的申请逻辑 |
**依据**：本项目需求书明确离线优先、框选区域限定；翻译类软件泄密风险集中于截图与 OCR 数据的非预期外传。
## 6. DSH 插件与供应链限制
| 编号 | 限制项 | 具体要求 |
|------|--------|----------|
| DSH-01 | 插件加载范围 | 开发期间 DSH 仅加载本项目自行开发的插件（`dsh-plugin-screen-ocr`、`dsh-plugin-translate`）。禁止从外部来源（npm、GitHub、论坛）加载未经审核的第三方 DSH 插件 |
| DSH-02 | 依赖引入审查 | AI 建议引入的任何新依赖（npm/cargo/pip）须经人工确认。检查项：包名是否与建议一致（防 typosquatting）、周下载量是否 >1000、最近发布时间是否 >30 天、是否有已知漏洞 |
| DSH-03 | 禁止幻觉包 | 如果 AI 建议的包名在官方 registry 中不存在或信息明显可疑，项目负责人有权直接拒绝，不执行安装 |
| DSH-04 | 插件审计 | 在连接真实翻译 API 或加载混元模型之前，运行 DSH 安全审计工具（如 `dsh-security-audit`）检查暴露面 |
**依据**：OWASP LLM04（供应链）为 2026 年重点关注风险；AI 建议的包名约 5–20% 不存在，存在 slopsquatting 攻击面。
## 7. 日志与遥测限制
| 编号 | 限制项 | 具体要求 |
|------|--------|----------|
| LOG-01 | 禁止远程上报 | AI 不得在代码中添加任何将 OCR 原文、译文、用户配置、截图数据发送至远程服务器的逻辑（用户自配置的翻译 API 端点除外，且仅发送翻译请求所需的文本） |
| LOG-02 | 日志内容 | 调试日志中不得包含 OCR 原文全文、译文全文、用户 API Key。日志可记录操作类型（如“OCR 完成，长度 42 字符”），不记录内容本身 |
| LOG-03 | 遥测开关 | 如未来引入遥测，必须默认关闭，且遥测代码的生成须经专项审批，本限制书 v1.0 不授权任何形式的遥测代码生成 |
## 8. 高风险代码模式的强制审查
AI 生成的代码若涉及以下模式，**必须经人工逐行审查后方可合并**，不得以“测试通过”为由跳过：
| 模式 | 审查要点 |
|------|----------|
| 网络请求构造 | URL 是否来自用户配置而非硬编码；是否仅向 `baseUrl` 发送；是否有超时限制 |
| 文件写入 | 写入路径是否在项目目录或用户配置目录内；是否可能覆盖用户数据 |
| 加密/解密 | 是否使用标准库（非自实现）；密钥来源是否安全；IV/Nonce 是否随机生成 |
| 凭据传递 | Key 是否仅在内存中传递；是否可能被日志、异常消息、序列化输出捕获 |
| 子进程启动 | 启动的命令行参数是否可控；是否可能被注入 |
| 权限申请 | 申请的权限是否与功能严格对应；是否有更小权限的替代方案 |
**依据**：AI 生成的代码倾向于宽松的输入处理和安全模式，需按未审 PR 对待。
## 9. 审批与例外流程
### 9.1 常规约束
本限制书所有条目默认生效，AI 在开发过程中应主动遵守。DSH 会话应使用 `workspace-write + ask` 权限预设，使越权操作触发人工审批。
### 9.2 例外申请
如开发确实需要临时突破某条限制（如调试需要读取系统字体目录以验证 OCR），须由项目负责人书面审批，记录：
- 突破的条目编号
- 原因与必要性
- 操作范围与持续时间
- 回滚方案
例外记录存入 `$PROJECT_ROOT/security/exceptions/` 目录，M5 交付前逐条核查并确认已回滚。
### 9.3 违规处理
发现 AI 违反本限制书时：
1. 立即终止当前 AI 会话。
2. 检查 `git diff` 和文件系统变更，确认是否有敏感数据泄露或环境破坏。
3. 如涉及凭据泄露，立即轮换相关 Key。
4. 记录事件至 `security/incidents.md`，更新限制书以覆盖该场景。
## 10. 交付前核查清单
M5 交付前，由项目负责人逐条核查：
| 编号 | 核查项 | 通过标准 |
|------|--------|----------|
| C-01 | 代码中无硬编码凭据 | `gitleaks` 或人工扫描通过 |
| C-02 | 无向非用户配置端点的网络请求 | 代码审查确认所有网络请求目标来自用户配置 |
| C-03 | 日志无敏感内容 | 抽查调试日志，无 OCR 原文、译文全文、Key |
| C-04 | 依赖列表已审查 | `package.json` / `Cargo.toml` 中所有依赖有记录和审查结论 |
| C-05 | 截图临时文件已清理 | `$PROJECT_ROOT/tmp/` 为空或仅含测试合成图 |
| C-06 | 权限申请与需求书一致 | 宿主壳 manifest 中权限项与 F-09/F-10 对应 |
| C-07 | 例外记录全部关闭 | `security/exceptions/` 中无活跃例外 |
